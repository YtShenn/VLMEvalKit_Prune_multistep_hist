# 面向 Prefill 与图像编码加速的研究思路整理

本文档总结了围绕当前项目中 `prefill` 阶段与 `image encode` 阶段加速的若干研究方向，重点关注：

- token 剪枝
- 多步 GUI / AndroidControl 轨迹任务
- 历史截图场景
- 具有一定创新性、可发展为论文工作的方向

## 一、背景与出发点

结合当前仓库已有实现，已经具备两类很有价值的基础能力：

- LLM `prefill` 路径中的中层 ROI visual token 剪枝
- 单样本内的 stateful template prefill / KV cache 复用

如果继续往前推进，最值得做的并不只是“再设计一个 token pruning 方法”，而是围绕**多步轨迹任务的时序冗余**来做更有针对性的加速方法。这类方向相比通用剪枝更容易讲出新意，也更适合形成完整论文。

## 二、统一记号与理论速度公式

为了统一分析，后文使用如下记号：

- `P`：单张图片进入 LLM 前的 visual token 数
- `V`：一个 prompt 中总 visual token 数
- `T`：一个 prompt 中的文本 token 数
- `L`：LLM 总层数
- `l`：在第 `l` 层之后把 visual token 从 `V` 压缩到 `K`
- `K`：LLM 内剪枝后剩余的 visual token 数
- `E`：视觉编码器总层数
- `e`：在第 `e` 层后做视觉侧 token condensation / pruning
- `r`：视觉侧压缩比例，即 patch token 从 `P` 变成 `rP`

忽略常数项，并假设 attention 是主要瓶颈时，可得到近似理论速度上界：

- 视觉编码理论加速：
  `S_encode ~= 1 / ( e/E + (1-e/E) * r^2 )`
- LLM prefill 理论加速：
  `S_prefill ~= 1 / ( l/L + (1-l/L) * ((T+K)^2 / (T+V)^2) )`

这些公式更适合理解“理论上能快多少”，不是直接等价于真实端到端速度。

## 三、研究方向 1：轨迹感知的视觉增量缓存

### 1. 核心思想

在多步 GUI 任务中，相邻两步截图通常高度相似。与其每一步都对历史截图完整重新编码，不如只对变化区域进行编码，对未变化区域直接复用上一步缓存的视觉特征。

### 2. 可能的实现方式

- 先用一个轻量变化检测器比较相邻截图
- 把图像切成 tile 或 patch
- 只重新编码发生变化的 patch
- 对未变化 patch 直接复用上一时刻的视觉 encoder 输出
- 最后加一个轻量 refinement 模块，缓解 patch 边界误差

### 3. 为什么有论文价值

这不是一般意义上的“通用 token 剪枝”，而是**专门面向多步 GUI 轨迹任务的增量视觉编码**。因为此类任务天生存在强时序冗余，研究动机和场景都很自然。

### 4. 理论加速上界

设变化 patch 的比例为 `rho`。

如果前 `e` 层仍然处理整张图，而后续层只处理变化区域，那么：

- 二次复杂度近似：
  `S_encode ~= 1 / ( e/E + (1-e/E) * rho^2 )`
- 更保守的线性近似：
  `S_encode ~= 1 / ( e/E + (1-e/E) * rho )`

示例：

- `e/E = 1/4`
- `rho = 0.2`

则：

- 二次近似约为 `3.57x`
- 保守线性近似约为 `2.50x`

### 5. 更现实的预期

如果实现得比较好，端到端在图像编码占比较高的场景中，比较可信的目标是：

- `2.0x - 3.5x`

## 四、研究方向 2：历史截图到紧凑记忆 token 的压缩

### 1. 核心思想

历史截图不应该长期以“完整 visual token 序列”的形式保存在 prompt 中，而应被压缩成少量 task-aware memory token，再送入 LLM。

换句话说，历史信息更像“状态”，不应该一直以高成本的原始视觉证据形式存在。

### 2. 可能的实现方式

- 对每张历史截图先做视觉编码
- 使用一个压缩模块把每张历史图从 `P` 个 patch token 压成 `m` 个 memory token
- 当前截图保留高分辨率 token
- 历史截图只保留压缩后的记忆表示
- 这个压缩过程可以用任务指令、历史动作等信息进行条件化

### 3. 为什么有论文价值

这条线的创新点不只是“减少 token 数”，而是提出一种新的历史建模方式：**把多步轨迹中的历史截图从原始感知证据转化为紧凑状态表示**。

### 4. 理论加速上界

设有 `H` 张历史图：

- 原始 visual token 数为：`(H+1)P`
- 压缩后 visual token 数为：`P + Hm`

则 prefill 理论加速近似为：

`S_prefill ~= ((T + (H+1)P)^2) / ((T + P + Hm)^2)`

示例：

- `H = 4`
- `P = 256`
- `m = 16`
- `T = 128`

则：

- 原始总长度：`1408`
- 压缩后总长度：`448`
- 理论 attention 主导加速约为：`9.9x`

需要注意，这个数字偏乐观，是理论上界。更现实的端到端速度提升可能在：

- `2x - 4x`

### 5. 论文定位建议

这条方向更像方法论文，主线可以叫：

- 多步 GUI agent 的历史状态压缩
- 基于 memory token 的历史截图建模

## 五、研究方向 3：在进入 LLM 前的早期视觉 token 凝聚

### 1. 核心思想

你们当前更多是在 LLM 中段剪掉 visual tokens。更完整的思路是把 token condensation 前移到 vision encoder 内部，在进入 LLM 前先把低重要度 patch 合并。

### 2. 可能的实现方式

- 在视觉编码器第 `e` 层后做 text-conditioned patch merge
- ROI 区域 patch 保持原分辨率
- 非 ROI 区域 patch 合并为 super token
- 再把压缩后的 token 送入 projector 和 LLM
- 

**版本 B：Action-conditioned 压缩**
更贴 GUI 任务。

做法：

* 每张历史图不仅输入图像，还输入该步对应动作文本
* 用动作 token 去引导历史图 patch token 的压缩
* 让输出 state token 更偏“操作后状态”而不是“图像内容摘要”

比如：

* 历史动作是 `CLICK search box`
* 压缩器更关注点击后页面结构变化、输入框激活状态、键盘是否弹出等

这个版本更容易讲成“动作感知状态建模”。

### 3. 为什么有论文价值

这条线不是单点优化，而是同时加速：

- 图像编码阶段
- LLM prefill 阶段

因此比只做 LLM token prune 更容易写成一个完整系统。

### 4. 理论加速上界

视觉侧：

`S_encode ~= 1 / ( e/E + (1-e/E) * r^2 )`

LLM prefill 侧：

使用压缩后的 token 数代入：

`S_prefill ~= 1 / ( l/L + (1-l/L) * ((T+K)^2 / (T+V)^2) )`

示例：

- `E = 24`
- `e = 6`
- `r = 1/4`

则：

- `S_encode ≈ 3.37x`

如果进入 LLM 后又进一步从 `256 -> 64`，并设：

- `L = 32`
- `l = 8`
- `T = 128`
- `V = 256`
- `K = 64`

则：

- `S_prefill ≈ 2.29x`

如果视觉编码与 prefill 两部分占比接近，一个粗略端到端上界约为：

- `2.7x`

### 5. 论文定位建议

这是一个非常适合系统论文的方向，因为它自然形成“双阶段 token economy”：

- 视觉侧先压缩
- LLM 侧再精剪

## 六、研究方向 4：跨 step 的多模态前缀增量缓存

### 1. 核心思想

当前 `stateful template prefill` 的 cache 复用主要还是单样本内的。下一步更有价值的方向是：**跨 step 复用多模态 prefix cache**。

在多步轨迹中，第 `t+1` 步的 prompt 很大一部分其实就是第 `t` 步 prompt 的扩展版本，因此不应该每一步都从零 prefill。

### 2. 可能的实现方式

- 在第 `t` 步结束时缓存“历史部分”的 multimodal KV
- 第 `t+1` 步只追加：
  - 新增的一张截图
  - 新增的一条历史动作
  - 当前 step 的尾部文本
- 通过 position remap 或稳定位置编码策略保证缓存可复用

### 3. 为什么有论文价值

这不是普通的 decode cache，而是**跨 step 的多模态前缀继承**。它与多步 agent 任务高度匹配，也比单样本 slot cache 更有新意。

### 4. 理论加速上界

假设窗口中始终保留 `H` 张历史图和 1 张当前图。

从头 prefill 的 attention 代价近似为：

`(T + (H+1)P)^2`

而增量 append 的代价近似为：

`Delta * (T + (H+1)P)`

其中 `Delta` 大致是一张新图加少量文本。

当 `T << HP` 时，理论上 prefill attention 加速可接近：

- `H + 1`

示例：

- `H = 4`

则 attention 主导下理论上界接近：

- `5x`

更保守地，如果 `Delta ≈ 1.3P`，则约为：

- `3.85x`

### 5. 论文定位建议

这可能是当前项目设定下**最强的系统论文方向**之一，因为它和已有 stateful template prefill 有明显延续关系。

## 七、研究方向 5：精度约束下的自适应 token 预算调度器

### 1. 核心思想

不要对所有样本使用固定的：

- history 长度
- prune layer
- keep ratio

而是为不同样本动态决定不同的 token 预算与剪枝策略。

### 2. 可能的实现方式

使用一些 cheap feature 预测每个样本需要的预算，例如：

- 任务类型
- history 长度
- 截图复杂度
- 低层 attention entropy
- 预测动作类别

然后输出：

- history 保留几张图
- visual token 保留多少
- 在哪一层 prune

目标是：在满足准确率约束的前提下，让 token 成本最小。

### 3. 为什么有论文价值

这条方向把静态剪枝升级成了**预算调度问题**，很适合做 latency-accuracy Pareto 分析，也容易与其他机制组合。

### 4. 理论加速上界

设：

- 简单样本比例为 `p`
- 简单样本预算为 `K1`
- 困难样本预算为 `K2`
- full baseline 预算为 `K_full`

则平均 prefill 成本近似为：

`C_avg = p*(T+K1)^2 + (1-p)*(T+K2)^2`

相对 full budget 的理论加速为：

`S ~= (T+K_full)^2 / C_avg`

示例：

- `p = 0.7`
- `T = 128`
- `K_full = 256`
- `K1 = 48`
- `K2 = 128`

则理论平均加速约为：

- `2.46x`

### 5. 论文定位建议

更适合作为一个调度层，叠加在更强的主机制之上，而不是单独成为整篇论文唯一核心。

## 八、我最推荐优先做的 3 个方向

如果只优先推进一条主线，我建议按下面顺序考虑：

1. 跨 step 的多模态前缀增量缓存
2. 轨迹感知的视觉增量缓存
3. 历史截图到紧凑记忆 token 的压缩

## 九、为什么这 3 个方向最值得优先做

### 1. 跨 step 的多模态前缀增量缓存

优点：

- 系统论文味最强
- 与现有 `stateful template prefill` 延续性最好
- 与多步轨迹任务最匹配

### 2. 轨迹感知的视觉增量缓存

优点：

- 最贴合 GUI 轨迹数据特性
- 能利用强截图冗余
- 动机直观，实验也容易设计

### 3. 历史截图到紧凑记忆 token 的压缩

优点：

- 方法创新性最强
- 能从“状态建模”角度讲新故事
- 不只是剪枝，而是重新定义历史信息的表示方式

## 十、一个更强的组合型论文方向

如果想做一篇更完整、故事更强的论文，我更推荐把两个方向组合起来：

`面向多步 GUI Agent 的状态压缩：视觉增量缓存 + 历史记忆 token`

可以分成两个部分：

- Part A：基于截图变化的视觉增量编码 / 缓存
- Part B：把历史截图压缩成少量 state / memory token

这样论文的主线会比“单纯做 token pruning”更完整：

- 视觉编码阶段减少重复计算
- LLM prefill 阶段减少冗余 token
- 保持多步决策能力

## 十一、现实中更可信的速度目标

理论上界通常会比较漂亮，但真正落地时，更建议把预期分成以下几个档位：

- 只做 LLM 中段 visual pruning：
  `1.3x - 2.0x`
- 做 early vision condensation + LLM pruning：
  `2.0x - 3.0x`
- 做跨 step 的 delta cache 或 multimodal prefix cache：
  `2.5x - 4.0x`
- 做 history-to-memory 压缩并配合缓存：
  `3.0x - 5.0x`

最后这一档实现难度最高，但如果做出来，论文价值也会最高。

## 十二、最终总结

从当前项目出发，最有论文潜力的方向，不是单纯继续做一个通用 token pruning，而是围绕**多步轨迹任务中的重复视觉内容、重复历史上下文和历史信息压缩**来设计新的加速机制。

一句话概括：

- 最像系统论文的方向：
  `跨 step 的多模态前缀增量缓存`
- 最像任务驱动创新的方向：
  `轨迹感知的视觉增量缓存`
- 最像方法论文的方向：
  `历史截图到紧凑记忆 token 的压缩`

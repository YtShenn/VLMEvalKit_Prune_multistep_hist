**核心原则**

不要按“方法名字”对齐，而要按**资源预算**对齐。GUI 历史压缩方法的形态不同，但最后都会影响几个共同量：

* 历史视觉 token 数
* 总 prompt sequence length
* prefill FLOPs
* vision encode FLOPs
* end-to-end wall time
* peak memory
* step SR / grounding / type acc

所以论文里应该同时报：

1. **Equal token budget** ：大家用差不多的历史视觉 token 数。
2. **Equal FLOPs budget** ：大家用差不多的 e2e FLOPs 或 prefill FLOPs。
3. **Equal latency budget** ：大家限制到相近 wall time。
4. **Best Pareto frontier** ：每个方法扫一组压缩率，画 SR-speed 曲线。

**具体怎么设**

建议定义一个统一预算变量：

```
history compression ratio r =
compressed_history_visual_tokens / full_history_visual_tokens
```

然后每个方法都扫：

```
r ∈ {1.0, 0.75, 0.5, 0.25, 0.125}
```

对应：

* `1.0`: full history
* `0.75`: 轻压缩
* `0.5`: 中等压缩
* `0.25`: 强压缩
* `0.125`: 极强压缩

对不同方法，把它们各自调到接近这个 `r`：

| 方法               | 怎么控制 r                                                       |
| ------------------ | ---------------------------------------------------------------- |
| low-res history    | 调整历史图 long edge / max pixels                                |
| frame dropping     | 保留最近 k 张历史帧                                              |
| thumbnail-only     | 调整 thumbnail 分辨率                                            |
| ROI-only           | 调整 ROI long edge 或 crop size                                  |
| State Packet       | 调整 thumbnail + ROI 的 token 总量                               |
| random/center crop | 调整 crop size                                                   |
| token pruning      | 调整保留 token 比例                                              |
| history resampler  | 调整 resampler 输出 token 数                                     |
| KV compression     | 调整 KV budget，但要单独标注它压的是 KV，不是 input visual token |

**主表不要塞太多压缩率**

主表建议只选一个代表预算，例如：

```
r ≈ 0.25
```

因为你的 State Packet 当前大概就是把历史 token 压到很低，且已有明显收益。

主表行可以是：

| Method | Hist. token ratio | SR | Grounding | Type | Total s | Prefill s | Decode s | FLOPs |
| ------ | ----------------- | -- | --------- | ---- | ------- | --------- | -------- | ----- |

然后补一个图：

```
x-axis: avg_total_wall_s 或 avg_e2e_flops
y-axis: SR
每条线一个方法，点是不同压缩率
```

这个图会比单表有说服力。

**不同类型方法怎么公平**

我建议分成三类比较，不要硬混成一个表后强行判胜负。

第一类：**输入级历史压缩**

这些和 State Packet 最公平：

* low-res history
* frame dropping
* thumbnail-only
* ROI-only
* random crop
* center crop
* State Packet

它们都改变进入 VLM 的历史截图内容，主要比：

* prompt tokens
* vision encode FLOPs
* prefill FLOPs
* SR

这是你的主战场。

第二类：**token/feature 级压缩**

例如：

* historical screenshot token pruning
* foreground/background pruning
* recency budget pruning
* history resampler
* UI-Hawk resampler
* OdysseyAgent resampler

它们不一定改变原图，而是压 visual features/tokens。比较时用：

* compressed visual token count
* LLM input length
* e2e FLOPs
* SR

注意写清楚是否需要训练。你的优势是：

```
training-free + plug-in + no architectural change
```

第三类：**KV/cache 级压缩**

例如：

* GUI-KV
* ST-Lite

这类压的是 KV cache，不一定减少 image encode/prefill，所以不能直接说同一个 `history token ratio`。更公平的是：

* equal decode KV budget
* equal end-to-end latency
* equal memory budget

并且可以强调互补：

```
State Packet reduces visual input and prefill cost;
GUI-KV/ST-Lite reduce KV cache and decode cost.
```

最好把它们放在 secondary comparison 或 appendix，而不是主表核心对手。

**一句话实验标准**

你可以在论文里这样定义公平比较：

> For all history-compression baselines, we sweep compression budgets and compare methods under matched historical visual-token ratios. We further report Pareto frontiers over success rate, latency, and FLOPs, since different methods trade off information retention and computation at different layers.

这样就不会被质疑“压缩率不一样所以不公平”。

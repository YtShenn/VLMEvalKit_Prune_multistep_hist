
确实，你现在观察到的问题本质上是：**像素差分检测的是“渲染差异”，不是“语义变化”**。明暗遮罩、键盘重绘、滚动抖动、状态栏时间、动态背景都会把像素差分带偏。要做得鲁棒，建议从“像素差异”升级到“结构/语义差异”。

我觉得最适合你这个项目的路线是下面几类，按可落地程度排序。

**1. Layout-Aware Diff：基于 UI 结构的差异检测**
这是我最推荐的主路线。不要直接比较像素，而是先从截图中提取 UI 元素，再比较前后帧的元素集合。

可以提取这些元素：

- OCR 文本框：文字内容、位置、字体块 bbox。
- 图标/按钮区域：用边缘、连通域、SAM、UIED 或轻量 detector 提取。
- 大块面板：bottom sheet、dialog、keyboard、toast、dropdown。
- 可交互区域先验：输入框、按钮、列表项、菜单项。

然后做前后帧匹配：

- bbox IoU 高、文本相同：认为是同一个元素。
- bbox 相近、文本变化：标记为内容变化区域，比如输入框从空变成 `US military`。
- 新出现元素：标记为新增 ROI，比如底部卡片、弹窗菜单。
- 消失元素：可选保留其邻近区域，帮助模型理解状态变化。
- 大面积背景变化但 UI 元素没变：忽略或降权。

优点是非常抗遮罩、抗亮度变化，因为它关注“控件和文字有没有变”，不是每个像素有没有变。对 AndroidControl 很合适，后续迁移 GUI Odyssey 也合理。

**2. Illumination-Invariant Diff：抗明暗变化的结构差分**
如果想保留零训练、低成本，可以把当前像素差分换成更鲁棒的结构差分。

不要用原始 RGB 差分，而用：

- `gradient magnitude / edge map`：关注边界结构。
- `local contrast normalized image`：先减局部均值、除局部方差，削弱遮罩和亮度变化。
- `SSIM residual`：结构相似度差异，比 RGB diff 更抗整体变暗。
- `Census Transform / Rank Transform`：经典视觉里很抗光照变化，只比较邻域相对明暗排序。

这一类可以作为当前代码的直接替代项：先做 `illumination normalization`，再算结构残差，再出 ROI。它不如 layout-aware 语义强，但改动小，很适合 v2。

**3. Feature-Space Diff：用视觉特征而不是像素比较**
把前后图切成 patch，用预训练视觉模型提特征，然后比较 patch embedding。

可用模型：

- DINOv2：更偏视觉结构和物体区域，适合找“语义变化”。
- CLIP/SigLIP：更语义，但对细粒度 UI 文本不一定够敏感。
- SAM encoder features：适合区域级变化。
- OCR text embedding + visual embedding 混合：适合 GUI。

做法是：

- 把截图分成网格 patch，比如 `16x16` 或 `24x24`。
- 对每个 patch 提 feature。
- 计算 cosine distance。
- 聚合相邻高差异 patch 成 ROI。
- 对状态栏、导航栏、键盘背景这类区域加先验过滤。

优点是对明暗遮罩更稳；缺点是会增加一点预处理耗时，而且对文本输入这种细粒度变化可能要配 OCR 才更准。

**4. Action-Conditioned Diff：结合上一动作约束变化区域**
前后图差异不应该只看图，还应该看动作。比如：

- `type/text input`：优先检查输入框、候选栏、键盘区域，不做全局 shift。
- `tap menu`：优先检查 tap 点附近、弹窗、bottom sheet、overflow menu。
- `scroll/swipe`：允许全局位移对齐，重点保留新暴露区域。
- `back/home`：大概率是全局页面切换，直接 full。
- `long press`：关注触点附近和上下文菜单。

这条路线很适合论文，因为它不是单纯图像 diff，而是 **action-conditioned visual state delta**。也就是说：同样的像素变化，在不同动作下意义不同。

**5. Accessibility / View Hierarchy Diff：如果能拿到树，这是最强信号**
如果 AndroidControl 或后续环境能拿到 view hierarchy，那么直接比较 UI tree 会比截图稳很多。

比较内容包括：

- node text
- content description
- class name
- clickable/enabled/focused/selected
- bounds
- hierarchy path

然后把变化 node 的 bounds 映射回截图，作为 ROI。这个方法几乎不受遮罩、亮度、壁纸、动态图影响。缺点是数据集/推理环境不一定总有 hierarchy，所以可以作为 optional oracle 或增强版。

我建议你的方法可以设计成一个组合框架：

```text
Robust Current Delta Packet
= Action-conditioned routing
+ Layout-aware UI diff
+ Illumination-invariant structural diff
+ Full fallback for true scene changes
```

具体优先级我会这样排：

1. 先做 `Action-Conditioned + Illumination-Invariant Diff`，这是当前代码最容易改的零训练版本。
2. 再加 `OCR/Layout-Aware Diff`，让输入框、菜单、底部卡片这类 GUI 变化更准。
3. 最后加 `DINO/CLIP feature diff` 作为语义补充，用于图片内容变化、复杂 App 页面。

论文角度，最有新意的表述可以是：

**从 pixel delta 转向 intent-aware semantic delta：当前帧不是被压缩成一张小图，而是根据上一动作预测哪些视觉状态变量可能改变，再用鲁棒结构/语义差异提取当前帧的最小充分证据。**

落到你的问题上，我建议下一版不要继续调 RGB diff 阈值了，那个方向会越调越碎。我们应该把当前模块改成两阶段：先根据动作类型判断允许变化的区域和模式，再用抗光照的结构差分/OCR diff 生成 ROI。
